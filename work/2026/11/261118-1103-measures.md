## Intent

The person raised two more points:

1. Track how long each feature or bug fix took, so that there are data to estimate similar work in the future.
2. Use those data to understand how flexible to change the system being built is: in general, adding a gate, a new
   workflow or a new capability to Honsha should not require rewriting the whole codebase.

A proposal was made in answer, and the person approved it: measures derived from git with nothing typed by hand, a kind
for each work item, and an expectation per kind of how many existing files a change touches. Tokens per session are left
to a later item, as an assumption to try first. Asked on 2026-11-18, in the chat of a session on the kit.

## Scope and acceptance criteria

### In scope

- What is measured for each work item, and how it is derived.
- A kind for each work item, and per kind how many existing files a change is expected to touch.
- A script that prints the measures of the items of a repository, including the items merged before it existed.
- The upkeep review using the measures.

### Out of scope

- Tokens, model and active time per session: they need a hook reading the platform's transcripts, an assumption to
  try first, in its own item.
- An index or a board of the measures: phase 2 of the plan.
- The hosting service: the measures come from git only.

### Boundaries

- Nothing is typed by hand except the kind, chosen when the record is created like the size.
- Records merged before this item are not rewritten; the script measures them without a kind.

### Acceptance criteria

1. The workflow says what is measured for an item and how each measure is derived from git: the intervals of agent
   work, of waiting for the person's approval and of review, and the size of the change in files and lines, with
   existing files and new files counted apart.
2. The record's front matter has `kind`; the profile lists the kinds of a project, each with the most existing files
   a change of that kind is expected to touch; a default list holds when a profile has none.
3. `node checks/measures.mjs` prints, for every merged item of the repository, its measures and whether it touched
   more existing files than its kind expects. It works on any hosting service and has its test.
4. The kit's profile lists its own kinds and expectations: a gate, a rule, a flow, a capability, a fix, upkeep.
5. The upkeep review reads the measures and reports the items over their expectation.
6. The kit's `verify` list passes; the core rules, the template, the worker and the checker stay within budget.

## Strategy

### Facts it rests on

Measured on 2026-11-18 for the kit's ten merged items, from git and the pull requests: from creation to merge between
12 minutes and 5.5 hours (16 hours for the first, overnight); 2 to 30 files; 3 to 15 commits. Every change to a rule
touched 4 to 6 existing files before item `261117-2114` put each rule in one place. A gate is a line of text in a
profile that the checker reads: adding one touches one existing file and no code.

### Design

- **Measures, all from git, in the workflow's new section 19:**
  - _created_: the identifier is the creation time;
  - _strategy_ and _approval_ (full items): the commit times of the two record-only commits;
  - _delivered_: the time of the closing commit, the last commit of the item before the merge;
  - _merged_: the time of the merge commit on the default branch whose second parent holds the item's commits;
  - intervals: agent work (created to strategy, plus approval to delivered; created to delivered for other sizes),
    waiting for approval (strategy to approval), review (delivered to merged);
  - size: commits, lines added and removed, existing files changed, new files added, from the item's diff against
    its merge base.
- **Kind:** a new front-matter key `kind`, after `size`. The profile's `kinds:` maps each kind to the most existing
  files a change of that kind is expected to touch. Default when a profile has none: `feature: 10`, `fix: 5`,
  `upkeep: 5`, `change: 10`. The kit's own: `gate: 1`, `rule: 3`, `flow: 3`, `capability: 3`, `fix: 4`, `upkeep: 6`.
  A gate counts the profile; a capability counts the documents that point to its new files.
- **Script:** `checks/measures.mjs`, Node.js only, plain git; reads the profile's kinds with the existing reader,
  extended for one more key; prints one line per item, and marks an item over its kind's expectation. Its test builds
  a repository with two items, one over its expectation.
- **Review:** workflow section 18 and the monthly task's prompt in the home read `node checks/measures.mjs` and
  report the items over expectation as places where the kit is too coupled.
- **Core rules and template:** the template gains `kind` with a comment; the core rules say the kind is chosen with
  the size, in one clause, to stay within their budget.

### Plan

1. Profile reader: `kinds`; its tests.
2. `checks/measures.mjs` and its test.
3. Template, core rules, checker (the record has a kind from its profile), workflow sections 4, 18 and 19, the kit's
   profile, README.
4. Verification, the checker, the pull request, the closing commit. Then, in the home, the monthly task's prompt.

### Assumptions to confirm while building

- The merge commit of an item can be found from git alone for every merged item, including the first one.
- The closing commit's time is close enough to the opening of the pull request to stand for it.

### Risks

- **Expectations set by guess.** They are a first value; the monthly review shows where they are wrong, and a change
  to them is a line in a profile.
- **Measures read as targets.** The workflow says they are for estimates and for finding coupling, not to judge a
  session.

### Decisions for the person

1. **The kinds and their expectations** as above, for the kit and as the default for projects. Recommended as a first
   value, to correct with data.
2. **No measure typed by hand** apart from the kind. Recommended.
