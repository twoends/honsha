## Intent

The person asked, through the session that started this one, for three changes, after what happened in PR 16: the
closing commit of a record carried an absolute path into the user's folder, with the Windows user name, because the
checker quoted that path in its report and the report was copied into the record. The local verification had run
before the closing commit; only the pipeline's test `checks/public.test.mjs` caught it after the push.

1. Item 2 of the assessment of Honsha (its finding 2; decision D71 in the home's `decisions.md`): a `pre-push` git
   hook in a clone of the kit that refuses a push whose commits add personal content: the patterns that
   `checks/public.mjs` already checks, plus a word list kept outside the kit, in the home, whose location each clone
   sets locally (for example with `git config`) and never commits. It is to cost nothing on a clone without a word
   list, and to run the same check on the commits being pushed, not only on the working tree. The work is to say how
   the hook is installed in a clone, and whether the kit's own setup can install it without a manual step.
2. The checker (`agents/checker.md`) quotes only paths relative to the repository, never absolute ones, and stays
   within its budget of 7,600 characters, which it is near.
3. `.gitignore` gains `.claude/worktrees/`, which shows as untracked in the kit's main folder.

Given on 2026-11-18 by the session that started this one, for the person.

## Scope and acceptance criteria

### In scope

- A `pre-push` hook for clones of the kit, the script it runs, with its test, and its installation.
- The patterns of `checks/public.mjs` extended to take a word list, so that what counts as personal is defined in one
  place.
- The guard refusing a push that skips the hooks, with its test, and the core rules and the workflow saying so.
- The checker naming files only by their path from the repository's root.
- `.claude/worktrees/` in `.gitignore`.
- The README saying what the hook refuses and how a clone gets it.

### Out of scope

- The word list itself and its file in the home: personal, outside this repository (see "Decisions for the person").
- A hook for other projects that use the kit: D57 concerns the kit. A project that wants it can adopt the script later.
- Checking the history already published: it was cleaned by rewriting, and the replaced commit is checked from the
  home before publication.
- What the hosting service could check on its side.

### Boundaries

- No word of the list, and nothing that locates the home on this machine, enters the kit, its records or its commit
  messages. The test builds its samples at run time, as `checks/public.test.mjs` does.
- The hook's report never repeats what it found: it names the commit and, where there is one, the file and line.
- No new dependency; the plugin still needs nothing installed to run.
- Install scripts stay off (`.npmrc`, `ignore-scripts=true`; workflow, section 17).

### Acceptance criteria

1. In a clone with the hook installed, a push is refused when any commit it sends, and not already on a remote,
   adds a line, a file name, a commit message or an author or committer that `personal()` finds; the report names the
   commit, the file and the line, and not the text.
2. Content added by one commit and removed by a later one in the same push is still refused.
3. With `honsha.words` set in the clone's git configuration to a readable file, its entries are matched too,
   ignoring case, as whole words; with it unset, the push is checked against the patterns only, with no file read
   and no message; set to a file that cannot be read, the push is refused with a line saying so.
4. The case of PR 16 is refused: a closing commit whose record quotes a path into a user's folder.
5. A clone gets the hook without a manual step when a session opens in it, and with one documented command
   otherwise; an existing `core.hooksPath` is left as it is.
6. The guard refuses `git push --no-verify` in a session; the core rules and the workflow's section 14.3 say so.
7. The checker names files only by their path from the repository's root, and stays within 7,600 characters.
8. `.claude/worktrees/` is ignored by git.
9. The kit's `verify` list passes, and the core rules with the template stay under the limit of
   `hooks/hooks.test.mjs`.

## Strategy

### Facts it rests on

- `checks/public.mjs` exports `personal(text)`: e-mail addresses that are not placeholders, and paths into a user's
  folder. `checks/public.test.mjs` runs it on the tracked files, in `verify` and in the pipeline. Its header already
  says the word list lives outside the repository, with a hook that reads it before a push.
- `.npmrc` turns install scripts off, and the workflow requires it (section 17), so npm's `prepare` cannot install the
  hook. The pipeline also runs `npm ci --ignore-scripts`.
- The repository declares its own settings in `.claude/settings.json`; a session opened in a trusted clone reads
  them. A hook declared there runs only in the kit's clones, unlike the plugin's hooks, which run in every project.
- Git cannot take its configuration from a committed file. `core.hooksPath`, set once in a clone's configuration,
  holds for all its worktrees; a relative value is resolved from the root of the worktree that runs the hook, so each
  worktree runs the hook its own branch holds.
- Git runs a hook with the root of the worktree as its directory and gives `pre-push` one line on its input for each
  ref pushed: local ref, local commit, remote ref, remote commit. On Windows it runs through Git Bash.

### Design

- **The hook:** `.githooks/pre-push`, a shell file of one command: `exec node checks/pushed.mjs "$@"`, committed as
  executable.
- **The script, `checks/pushed.mjs`:**
  - Reads the lines git gives. A deleted ref is skipped. The commits checked are those reachable from what is pushed
    and from no remote-tracking ref (`--not --remotes`): what was published already is not checked again, and a stale
    remote ref only makes the check wider.
  - One `git log -p -U0 --cc` over those commits gives, for each, its author, committer, message and the lines it
    adds, with their file and line. A merge contributes only what differs from all its parents: the resolution of its
    conflicts. Binary files are skipped.
  - Each piece goes through `personal()`. On findings it writes one line each, `<commit> <file>:<line> holds <kind>`,
    or `<commit> its message holds <kind>`, then the reason and that the person can push from their own terminal with
    `--no-verify` if a finding is wrong, and exits 1.
  - `--install` sets `core.hooksPath` to `.githooks` when no level of git's configuration sets it, and does nothing
    otherwise, silently.
- **The word list:** `personal(text, words = [])` in `checks/public.mjs` also reports each entry of `words` found as
  a whole word, ignoring case, as "a word from the personal list". `checks/pushed.mjs` reads the file that
  `git config honsha.words` names: one entry per line, blank lines and lines starting with `#` ignored. Unset: no
  file is read. Set but unreadable: the push is refused, since otherwise the protection would be off without anyone
  knowing.
- **Installation:** a `SessionStart` hook in the repository's `.claude/settings.json` runs
  `node checks/pushed.mjs --install` when the script exists, so a clone where a session opens gets the hook with no
  step of its own. The README gives the same command for a clone used without sessions, and the
  `git config honsha.words <file>` line for whoever keeps a list.
- **The guard:** `hooks/guard.mjs` refuses `git push` with `--no-verify`, with its own reason. The core rules'
  sentence on what a session never does gains "never skips the hooks of a push"; section 14.3 counts four kinds; the
  description in `hooks/hooks.json` follows. The person's own pushes are not affected.
- **The checker:** one sentence in "What you return": a file is named by its path from the repository's root, never
  by an absolute path. About 80 characters, within the 93 left.
- **`.gitignore`:** `.claude/worktrees/`.

### Plan

1. `checks/public.mjs` and its test: the `words` parameter.
2. `checks/pushed.mjs`, its test in temporary repositories with a bare remote, and `.githooks/pre-push`. The cases:
   each acceptance criterion from 1 to 5, a clean push, a deleted branch, commits already on the remote, a merge.
3. `.claude/settings.json`, the README.
4. The guard, its test, the core rules, section 14.3, `hooks/hooks.json`.
5. The checker, `.gitignore`.
6. The hook installed in this clone; a trial push of the branch, which runs it for real.
7. Verification, the checker, the pull request, the closing commit.

One worker, in sequence. Steps 1 to 3 are one commit, step 4 another, step 5 a third: three concerns a reviewer can
take one at a time.

### Assumptions to confirm while building

- A `SessionStart` hook declared in the repository's settings runs next to the plugin's, in the clone's folder.
- `git log --cc -U0` gives hunk headers from which the new line number can be read for ordinary commits and merges.
- A file committed with mode 100755 from Windows runs as a hook on Linux.

### Risks

- **A finding that is wrong blocks a push.** The patterns are those the pipeline already applies; a word list entry
  that is too common is the person's to fix. The person can push with `--no-verify`; only sessions are stopped.
- **A worktree on a branch older than the hook** has no `.githooks/pre-push`, and git runs nothing there. The
  pipeline's test still catches the patterns after the push. It ends when such branches are merged.
- **A clone used only from a terminal, never with a session,** has no hook until the README's command is run.
- **The guard matches text:** `git -c core.hooksPath=… push` gets past it. It stops a mistake, as section 14.3 says.

### Open work that touches the same files

- PR 16 (`work/261118-1532-home-direct-commits`) changes `hooks/guard.mjs`, `hooks/guard.test.mjs` and
  `docs/01-specs/WORKFLOW.md`.
- The session on `work/261118-1708-git-bash-paths` changes `hooks/guard.mjs`.

The change to the guard here is one more option of `git push` and its reason. When either merges first, `main` is
merged into this branch and the conflicts are resolved there.

### Measure

Against the 3 existing files a capability is expected to touch, this item touches about 11: the request bundles
three concerns, and the guard's rule reaches the core rules, the workflow and the hooks' description.

### Decisions for the person

1. **Installation without a manual step,** by a `SessionStart` hook in the repository's settings, and one command in
   the README for the rest. Recommended. The alternative is the README's command only.
2. **The guard refuses `--no-verify` on a push,** with one more clause in the core rules. Recommended: without it a
   session can skip the hook with one flag.
3. **A list that is set but cannot be read refuses the push.** Recommended.
4. **The word list on this PC,** outside this repository: a file in the home, which the person names and fills (the
   Windows user name, the names of their projects, providers and servers), and `honsha.words` set in this clone. This
   session can propose the entries from the home's documents and set the configuration, after the person approves
   the list; nothing of it is written in the kit.
