hub's writes to the home other than the registry's moves have no path, but pointed out that an idea could already be

## Scope and acceptance criteria

### In scope

- Where the home's backlog lives and how a record enters it and leaves it: an idea, a request kept for later, a
  `ready` item, a `dropped` one.
- The workflow's sections that name the backlog (1, 3.3, 5, 10), the architecture's layout of the home and its
  dispatch flow (sections 3.2 and 4.3), its index (section 3.4), which also reads the `backlog` branch,, and a script of `hub/` with its tests that writes the backlog.

### Out of scope

- The inbox with its verdicts and the lessons of a technology or of a host, which keep reaching the home in its work
  items; phase 3, which builds the inbox, decides whether they follow the backlog.
- The home's own instructions: once this item is merged, a home item points its "Dispatch" step to the script.
- The registry's moves.

### Boundaries

- The home's default branch still changes only through pull requests that the person merges, and the guard is not
  loosened.
- A captured record is on the hosting service as soon as it is written: nothing captured lives only on the host.
- The person does nothing for a capture to land: no pull request, no merge.
- The kit's rules name no hosting service.

### Acceptance criteria

1. The workflow says, in one place, that the home's backlog is a branch of its own, `backlog`, never merged, which
   the hub writes and pushes at once, and that a record leaves it when its item starts.
2. One command adds a record to the backlog and pushes it, and one removes it when its item starts; neither touches
   the home's working tree or its default branch.
3. Every document that places the backlog in `backlog/` of the home's default branch says the branch instead.
4. The script's tests cover a first capture on a home with no `backlog` branch yet, a second one, a removal, and a
   capture refused for a project that is not in the registry.
5. The profile's `verify` passes.

## Strategy

The rule that slows a capture down is that the home's default branch changes only through pull requests. The backlog
does not need to be on the default branch: a record there is not a change to anything, it is waiting. So the backlog
becomes a branch of the home of its own, `backlog`, that is never merged. Pushing to it is not a push to the default
branch, so the guard lets it through and no rule gets an exception.

- **Capture.** `node <kit>/hub/backlog.mjs add <project> <file>` checks the project against the registry of the
  home's default branch, commits the record to `backlog/<project>/` on the `backlog` branch in a temporary worktree
  (the code of `hub/projects.mjs` that does this is shared), and pushes that branch. One command, about a second, and
  the hub answers that the idea is in the backlog.
- **Start.** When an item of the backlog starts, `hub/backlog.mjs take <project> <id>` removes the record from the
  branch, pushes, and prints the record, which goes into the project's session as a dispatched request does.
- **Reading.** The hub's questions about a project's backlog read the `backlog` branch (section 10).
- **Commits.** A commit on `backlog` is one record added or removed, by the script, with a message it writes; the
  check of a work branch's commits does not run on it, as it is not a work branch.

Assumptions: the hosting service accepts a push to a branch other than the default one with no pull request, which is
what every work branch already does.

Risks: the backlog is not in the default branch, so a clone shows it only after `git fetch` and on that branch; the
hub reads it with the script, so the person does not have to.

Cost: about one full item: a script with its tests, and the documents that name the backlog.
