## Intent

The person asked for the record and the strategy of an item on the kit. Today a session opened in an installation's
home becomes the hub only through instructions that the installation writes itself, in the home's `CLAUDE.md`: answer
from the records, add a project with `hub/projects.mjs`, dispatch an item once `may-start` allows it, capture with
`hub/backlog.mjs`, follow the sessions it started. That procedure is the kit's behaviour, the same in every
installation, so every user of the plugin has to write it again. Each reorganisation of the kit also leaves it, and
the home's other notes, pointing at what moved: after item `261121-1321` they still cite the workflow by section
numbers that the item removed. The person observed that a plugin that others use should not make them edit their own
files to keep using it.

The direction asked for: the procedure as an agent of the kit, `honsha:hub`, beside `honsha:worker`, generic, which a
session opened in the home runs without the user writing instructions, once the platform has been checked for how; the
home keeping only what is the installation's, and the strategy naming what its `CLAUDE.md` still has to hold, if
anything; and the kit's interface for an installation written down once, as the only thing an installation's files
may cite, a change to which is a change to a public interface. The home's own change is an item of the home, after
this one. The strategy says whether the item fixes a defect or adds a capability, and leaves that to the person.

Asked on 2026-11-21, through the session of the kit's readiness review, which started the session that wrote this
record.

## Scope and acceptance criteria

### In scope

- `agents/hub.md`, the agent `honsha:hub`: the hub's procedure, generic.
- A hook of the kit that gives that procedure to a session opened in a home's own folder.
- `docs/01-specs/INTERFACE.md`: the kit's interface for an installation, written once.
- The rule that a document outside the kit cites the kit only by that interface, in the core rules (Documents).
- What the kit's scripts write into a home, citing the interface; the scripts' opening comments pointing to it.
- The tests of each, the budgets, the kit's profile, the README, the architecture and the workflow, where they say
  what the kit holds or how a session becomes the hub.

### Out of scope

- What the hub does. The procedure moves and becomes generic; no verb, script or rule is added to it or dropped,
  apart from the two steps that item `261121-1321` gave to the hub's instructions (see the strategy).
- The home: its `CLAUDE.md`, its decisions and its references to the kit change in an item of the home once this one
  is merged (strategy, "After the merge").
- How a session in a project runs the worker's procedure. A session that an application starts in a project runs
  with the platform's own prompt and the core rules, and the worker's file reaches it only if it reads that file; this
  session is one. It is a defect of its own, for an item of its own.
- A check, run in every project, that fails on a reference to a section of the kit: the rule comes first, and a check
  only if the rule proves not enough.
- A version for the plugin (O10).

### Boundaries

- The agent, the hook, the interface and every test fixture name no user, project, installation, folder, language or
  decision of an installation.
- A session outside a home receives at start what it receives today; the core rules' parts stay within the limits of
  `hooks/hooks.test.mjs`.
- Nothing that an installation can rely on today is renamed or removed: the item adds, and breaks nothing.

## Strategy

**Defect or capability.** Part of the item fixes a defect; part is, by the letter of D87 of the installation, a new
capability. The interface and the rule on references fix a defect: the kit says nowhere what an installation may rely
on, so its last reorganisation broke the home's references without a word, and the next one would again. Moving the
hub's procedure into the kit adds no verb, script or rule: the installation runs that procedure today, and what is the
same for every user belongs in the kit. But it ships as a new agent and a new hook, and the installation's plan places
the hub's session in its second phase, which D87 holds back until the first is done. This strategy reads the whole
item as a defect fix, the defect being that every installation has to write the hub; the kind is `fix` on that
reading. The person decides among:

- the whole item now;
- the interface and the rule now, and the hub's part after phase 1, as an item of its own (criteria 1 to 3, 12 and
  13, and the hub's share of 10 and 11, go with it, and the kind of each part is set again);
- all of it after phase 1, with the kind `capability`.

**What the platform offers, verified.** On this PC, Claude Code 2.1.325, in a scratch repository with the kit loaded
through `--plugin-dir`, with `claude -p`:

- The key `agent` of a project's `.claude/settings.json`, set to a plugin's agent by its full name (`honsha:worker`),
  makes the session's main thread that agent: after a one-line preamble of the platform, the agent's file is the whole
  system prompt, in place of the platform's own. The kit's hooks at a session's start still run, `CLAUDE.md` still
  loads, and the hook's input names the agent in `agent_type`. `--agent` on the command line wins over the key, and is
  named there too.
- The documentation adds: the key may sit in any settings file; a plugin's agent cannot carry `hooks`, `mcpServers` or
  `permissionMode`; a session in a worktree that the desktop application makes reads its settings, hooks and agents
  from the main checkout's root; every interface reads the same settings files.
- Not verified, and the documentation says nothing of either: whether the desktop application, the editor extensions
  and cloud sessions honour the key; whether an agent's system prompt keeps what the desktop application adds to the
  platform's, such as its means of starting and following other sessions, which the hub uses.

**How a session in the home becomes the hub.** Three ways were weighed.

- **The key `agent` in the home's settings,** `"agent": "honsha:hub"`. A file the home commits reaches every session
  of the home, those in its worktrees included, where the home's own items run, an assessment or a report: each would
  start as the hub. Only `--agent` on the command line overrides it, and this session found no such choice in an
  application that starts a session. The agent's prompt would also take the place of the platform's, and maybe of
  what the desktop application adds to it. It is also a line that each installation writes.
- **A hook of the kit** at a session's start: when the session's folder is the main working tree of a home and the
  session runs as no agent, the hook gives the hub's procedure, as the core rules' parts are given. A home is known by
  `registry.yml` at its root, the mark that the worker's verification and the pipeline already use. Nothing is written
  in the home; the kit's hooks run in the desktop application, where this session received the core rules through
  them; the platform's prompt stays; a session in a worktree of the home, where an item runs, gets nothing. The
  procedure arrives as context, as the home's `CLAUDE.md` gives it today, which works.
- **A skill, or an output style.** A skill enters only when the session invokes it, and the hub needs its procedure
  from the first message. A plugin's output style that applies itself does so in every project; one that the home's
  settings choose reaches every session of the home, as the key `agent` does.

The proposal joins the first two without the key. The procedure is written once, as the agent `honsha:hub`, so that
`claude --agent honsha:hub` runs it with its model, as an always-on host would start the hub; and the hook gives the
same file's body to a session in a home's own folder that runs as no agent. One file, two ways in, nothing in the home.

**What stays to try.** After the merge, in the desktop application: a session opened in the home's folder, outside a
worktree, receives the procedure, and a session that the hub starts in a worktree of the home does not (criterion
13). A hub opened in a worktree of the home gets nothing: the hub is opened in the home's own folder, which is where
the architecture already puts it.

**What the home keeps.** Its data and its choices: the registry, the backlog, the decisions, the radar, the lessons,
the plan, its profile and its settings. The installation's choices that its `CLAUDE.md` holds today become entries of
its decision log, which the hub reads before its first answer: the chat's language among them. The folder of a clone
of the kit is no longer needed, since the hub runs the scripts from the kit directory that the session receives at
start. A home's `CLAUDE.md` is then left with nothing to hold, and the home deletes it. One kept for another reason
must not hold the hub's procedure: it loads in every session of the home, its items' included.

**The interface.** A document of its own, `docs/01-specs/INTERFACE.md`, cited as `(interface, <heading>)`. The workflow
and the architecture are rewritten as the kit grows, for whoever changes the kit; the interface is what an
installation reads, and it changes only through a full item. It holds the list of criterion 4 and states the commands'
forms and the registry's shape, which leave the scripts' opening comments, so that they are stated once, where an
installation reads them. The core rules already make a change to a public interface full and a breaking change a stop
condition; the interface says that its list is the kit's public interface, the kit's profile makes every change to the
file full, and a test keeps the list and the kit equal in both directions. Adding a name is not breaking; renaming or
removing one, or changing a command's arguments or a file's shape so that what an installation holds no longer works,
is. Since the manifests carry no version (O10), a change reaches every installation at once, which is why a breaking
one stops for the person. Records keep the references they were written with, as history.

**The rule on an installation's documents.** In the core rules, under Documents, since a session of any project may
write such a document; records stay outside it, by the exception that part already makes.

**The agent's content.** The procedure that an installation writes today, made generic: the kit directory from the
start context, the installation's choices from its decision log, the home's files by the interface's names. Added to
it, the two steps that item `261121-1321` gave to the hub's instructions: `honsha:parallel-parts`, whose description
names the hub, before an item starts in a project where another runs; and the deferred checks that are due.

**Commits.** Two, each reviewable on its own: the interface, the rule, the references and the scripts' text, with
their tests; then the agent and the hook, with their tests and the documents that name them.

**Budgets.** Six thousand characters for the agent's file, whose procedure is about 3,500 today. The interface's budget
is its size once written, rounded up to the next thousand, plus 2,000. The total at a hub's start is the total of every
session plus the agent's budget.

**After the merge.** An item of the home, which the person approves on its own: it deletes `CLAUDE.md`; writes the
chat's language as a decision, and rewrites the decision that says how the hub is instructed; and rewrites by the
interface's names every reference to a section of the kit in the home's documents and radar entries. It takes the
place of the change to `CLAUDE.md` that item `261121-1321` planned for the home. The registry's header, which only the
script writes, follows at its next write.

**Risks.**

- Between this merge and the home's, a hub session receives the procedure twice, from the kit and from the home's
  `CLAUDE.md`, which say the same with the old references: the home's item is written at once, and the person can
  merge the two together.
- Context is weaker than a system prompt. It is how the hub is instructed today, and it works; `--agent honsha:hub`
  gives the stronger form where an interface allows it.
- A project that holds a `registry.yml` at its root is taken for a home, as the kit's checks already take it.
- The interface fixes names: a rename becomes a full item, and a stop when it breaks an installation. That is the
  intent.
- The installation is about to import its first project, whose entry the hub makes: the person decides whether that
  waits for the merge.

**Alternatives left out.** The key `agent` and an output style, for the reasons above. The interface as a section of
the architecture or of the README: the architecture is reorganised with the kit, the README is about trying and
changing the kit, and the interface must be the one place that an installation reads and that does not move.

**Parallel parts.** None: the agent's file names what the interface lists, and both parts change the README and the
architecture. The default model is enough.

**Measures.** About ten existing files against the four of `fix` (three of `capability`): the README, the architecture,
the workflow, the core rules' part, the kit's profile, the two hub scripts, `hooks/hooks.json` and the tests that read
them. The measure will mark the item over its kind's expectation, for that reason.
