## Intent

The person asked the hub for a change to the kit after a gap that a project's work item found. The kit's reusable
workflow, `.github/workflows/project.yml`, installs Node.js 26 with `actions/setup-node` and then runs the profile's
`setup` commands. Every Node.js 26 release carries npm 11, so a project whose `package.json` asks npm 12 through
`devEngines` stops at its first `npm ci` with `EBADDEVENGINES`, and the workflow offers no way to install another npm,
as it offers for Claude Code with its `claude-code` input. A host can keep one npm for all its projects, but the
pipeline starts from a fresh runner each time, so only the workflow can give it the npm a project needs. The change
gives `project.yml` an optional input that names the npm version to install before the setup, and says so where the
kit describes the caller file and its inputs.

## Scope and acceptance criteria

### In scope

- `.github/workflows/project.yml`: a new optional input, `npm`, and a step that installs that npm version after
  `actions/setup-node` and before the step that runs the profile's `setup` commands.
- `.github/workflows/verify.yml`: the kit's own `project` job passes an exact npm 12 version to the new input, so that
  the input runs on the kit's pull requests and pushes, as `claude-code` does.
- `docs/01-specs/INTERFACE.md`: the line on `project.yml` names its inputs `claude-code` and `npm`.
- `services/github/README.md`, "Checks on pull requests and on the default branch": the caller file's `with:` is
  described for both inputs, and "What it runs" says that the npm a caller names is installed before the setup.

### Out of scope

- Reading the npm version from a project's `package.json` (the alternative weighed under Strategy).
- Any project's caller file: the project's own item changes it once this item is merged.
- The Node.js version the workflow installs, and the kit's own `verify` job, which keeps the npm that Node.js 26
  carries.
- Any other package manager.

### Boundaries

- Four existing files, the most a fix is expected to touch.
- The input is optional and empty by default: a caller that does not name it gets the same run as today.
- The version reaches the shell through an environment variable, never interpolated into the script, as for
  `claude-code`. The token's permissions and the pinned actions do not change.

### Acceptance criteria

- `project.yml` declares the input `npm`, a string, not required, empty by default, with a description that says it is
  the npm version installed before the setup, none when empty.
- When the input is not empty, a step between `actions/setup-node` and "Prepare the checkout with the setup commands
  of the profile" runs `npm install --global "npm@$VERSION"` with the version from an environment variable, and then
  prints `npm --version`; when it is empty, the step is skipped.
- The `project` job of `verify.yml` passes `npm` with an exact npm 12 version, and the run of that job on this item's
  pull request shows the step installing that version before the setup and the setup passing under it.
- `INTERFACE.md` names the inputs `claude-code` and `npm` of `project.yml`, and nothing else in it changes.
- `services/github/README.md` describes `npm: "<version>"` under `with:` beside `claude-code`, with when a project needs
  it, and its "What it runs" says that the npm a caller names is installed before the setup.
- The profile's `verify` and the kit's record and commit checks pass, apart from a failure that this host's application
  control causes, which the pipeline then runs; the pipeline's result on the pull request is recorded.

## Strategy

**The design.** The new input follows `claude-code`: an optional string, empty by default, passed to the step through
`env:` and installed with `npm install --global`. It differs in one place, the order: `claude-code` is installed after
the setup, but the npm the input names must be in place before it, since the setup's first `npm ci` is what checks
`devEngines` and stops. So the step sits right after `actions/setup-node`. It prints `npm --version` after the install,
so that a run's log shows which npm the setup used. The input is named `npm`, after the package it installs, as
`claude-code` is named after its own.

**The alternative weighed: reading the version from the project's `devEngines.packageManager`.** It would need no word
in the caller, and the version would live in one place. It is not chosen:

- `devEngines` holds a range, such as `^12`, not an exact version: the pipeline would either install whatever is newest
  in that range, which the kit's pins avoid everywhere else, or need its own rule to pick one.
- `project.yml` is not only for Node.js projects, and where a project's packages are is the profile's `setup` to say:
  "the pipeline installs none of the project's packages itself". A `package.json` at the root may not exist, or may not
  be the one the setup uses.
- It is a second mechanism beside `claude-code`, where a caller already names what the runner needs, and it departs from
  the input that was approved for the project's item; a departure is the person's to decide.

A caller that names `npm` repeats a version its `package.json` allows; npm's own `devEngines` check at the setup's `npm
ci` keeps the two consistent, since a version outside the range stops the run.

**How the input is proven before a project relies on it.** The kit's `verify.yml` calls `project.yml` from this
repository at the pull request's own commit, and the job's comment says it is there so that a change to `project.yml`
runs on the kit's pull request before it reaches a project. Its `with:` gains `npm` with an exact npm 12 version, chosen
at the work as the newest 12.x release at least two weeks old, so the run on this item's pull request shows the step
installing it, `npm --version` printing it, and the kit's setup (`npm ci --ignore-scripts`) and `verify` passing under
it. That stays: every later change to `project.yml` runs the input again. The kit's `verify` job keeps the npm of
Node.js 26, so the kit is checked under both. No project's caller is pointed at a branch of the kit: that would change a
project's file for a test, and the kit's own run covers the same path.

**Plan.** One commit of the work after the approval: the two workflow files and the two documents, with the record's
log. Then the verification, the checker, and the closing commit with the pull request. No part runs in parallel: the
change is a few lines in four files that must agree.

**Assumptions.** npm 12 installs with `npm install --global` over the npm of Node.js 26 on `ubuntu-latest`; the kit's
lockfile is read by npm 12's `npm ci` as it is by npm 11's, as it is on this host, which has npm 12.

**Risks.** A future npm 12 release that refuses the kit's lockfile would fail the kit's `project` job, not its `verify`
job: the pin keeps that from happening unseen, and moving it is an ordinary update.

**Question for the person.** Pinning npm 12 in the kit's own `project` job is part of the scope above, as the proof
that lasts. If the person prefers that the kit's pipeline keep only the npm of Node.js 26, the proof is that run alone on
this pull request, with the pin taken out before delivery, which leaves the input untested afterwards.
